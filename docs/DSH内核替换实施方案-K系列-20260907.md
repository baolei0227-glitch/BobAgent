- ❌ 不目标：不改 SSE 协议、不改事件结算、不改 .md/游标、不改前端契约、不引第三方运行时（先自有 loop kernel，留替换位）。

## 3. 分步（K1→K4，每步含验证门）

### K1 会话上下文收敛（无行为变化）
- 内容：把 loop 内散落的状态声明收敛为一个 `KernelContext` 对象字面量（仍是局部闭包变量，仅归组）：messages/round/level/roundThinkingMode/needRebuildTools/completionConfirmUsed/chatStickyScenes 使用点改用 ctx.*。**module 级可变状态（chatStickyScenes/CacheGuard）不动**。
- 改动：route.ts 单文件内 refactor；文件：route.ts。
- 验证门：tsc 0；lint 新增 0；字节级对拍 3 条任务（纯问答/工具轮/挂起流）prefixSegments 与清理前一致；dev 200。

### K2 runtime services 抽取（动文件边界，不动行为）
- 内容：把盘点 §3 已抽象/可抽块落成 `src/lib/runtime/` 服务模块，route 改注入：
  - `services/tools.ts`：注册/执行/排序/mergeForcedMcp（从 tools.ts 与 route 胶水归位）+ CacheGuard（状态迁入服务，随 LoopSession 重建由服务持有全局单例→改 service 实例）；
  - `services/context.ts`：动态上下文链（NodeBridge/VisionBridge/PDF/项目路径/授权/偏好/OCR 事实/Coding 沙盒）provider 化，仍 prepend 末条 user；
  - `services/session.ts`：LoopSession（sticky/卡片等会话态）；
  - 其余（EventTrajectory/PendingHost/SkillService/CompactionService/Approval/ThinkingPolicy/ModelResolver/Usage/OutputFiles）多为已有 lib，收敛调用面为 service 包装。
- 改动：新增 src/lib/runtime/*；route.ts 大量换引用。
- 验证门：每抽一个 service 跑一次对拍（3 任务 prefixSegments 不变 + 单测不回归）；tsc 0；本阶段**不引入 hook 抽象**（行为面不漂移）。
- 风险：高。拆引用时 C2/帧序/落账三连顺序必须逐行对照；建议按"一个 service 一个 commit"粒度。

### K3 loop kernel 固化 hook（在 service 抽取稳定后）
- 内容：r0-r19 与 a-s 咨询链固化为显式 hook 接口（复用 tool-pipeline kind/phase）；"内核固有"块（轮调度/收帧/退出状态机/done 结算）留在 kernel 模块（route 或 `src/lib/chat/kernel.ts`）。
- 改动：新增 kernel 接口类型 + route 改调。
- 验证门：咨询顺序九个点与 §1.2 硬顺序一致（单测断言注册序）；对拍不变。

### K4 可替换性验收 + 可选：抽独立 kernel 模块
- 内容：route 壳瘦身完成；kernel 可作为模块被 route 与其他入口调用；输出"替换另一个 loop 的适配清单"（SSE/事件/pending/缓存四契约）。
- 验证门：完整回归清单 A-G（含人工项）过一遍。

## 4. 阶段门控（每 K 提交前）

1. tsc 0 / lint 新增 0 / vitest 全绿；
2. 3 类任务对拍：纯问答、工具轮、挂起型（ask/confirm）——`prefixHash` 四段一致 + `.trajectory` 事件类型集一致 + done 帧字节 diff 为空（除时间戳/taskId/usage）；
3. 前端冒烟：消息流/挂起弹窗/回放不受影响；
4. 任一失败 → 回滚该 K（保留上一 K 提交点）。

## 5. 风险与红线

- 缓存前缀失效（system/动态注入通道/工具排序任何漂移 → 全量缓存失效）：K2 每 service 对拍锁死；
- C2 reasoning 原样回传：任何"重建 assistant 消息"的 hook 不得 trim/改写（K2/K3 代码评审红线）；
- 帧序与前端 90s 契约：挂起/长操作 20s 心跳随 handler 迁移不得丢；
- 三连落账顺序（allToolCalls→conversationMessages→eventLog）为结算语义，抽服务时保持调用点原位（服务不吞顺序）。

## 6. 里程碑与建议节奏

K1（小）→ K2（大，拆 6-8 个 service，每个独立提交+对拍）→ K3（hook 固化）→ K4（验收）。建议 K1 与 K2 每个 service 之间穿插一次真实对话冒烟；K2 中途不回退则持续。

## 8. K 系列结论与建议

- K1-K3 已完成：loop 的**状态（KernelContext）/ 服务面（runtime services）/ 咨询链契约（TOOL_CONSULT_SEQUENCE + 自检）**三条边界显式化；动态上下文全链 provider 化且 C8 注入通道零改动；每步字节对拍通过。
- **不建议继续物理拆分 route 主循环**（K3-2 后的"执行器化/函数化"）：剩余耦合为深闭包依赖（send/kctx/帧序/三连落账），拆分收益（可读性）与回归风险不成比例；当前形态已满足"可替换性"所需的契约资产（SSE/事件/pending/缓存四契约 + 咨询点注册表）——若未来出现第三方 loop 接入需求，直接以这些契约为适配清单新建内核即可，无需先拆现循环。
- K4 验收口径 = 回归清单 A-G + 历次对拍资产（prefixSegments/事件集/字节模板），不再新增代码动作。
- 遗留：`src/lib/runtime/session.test.ts`（sticky 单测）可选补；route 存量 lint 债（4 error + 若干 warning，均 <3100 行、非改动区）建议单独立项。
