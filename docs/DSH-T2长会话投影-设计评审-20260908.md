# DSH T2 长会话「早期轮摘要投影」落点设计评审（2026-09-08）

> 关联：`docs/DSH完全对齐方案-20260908.md` §11（T1 已完成：tools 段 -14.9%，T2 待立项）。
> 性质：**只读评审 + 落点方案**，本文件不含业务代码改动。
> 目标语义：对齐 DSH「模型面 = 每轮派生的精简投影、真相存 append-only 日志」，在**不破坏前缀缓存**的前提下降低长会话每轮重发 messages 的输入 token。
> 依据：2026-09-08 对 `ChatNodeKernel.tsx` / `app/api/chat/route.ts` / `nodes/route.ts` / `lib/nodes/compact.ts` / `lib/context-limits.ts` / `lib/node-markdown.ts` / `lib/trajectory/*` 的逐行实读；实测数据来自本机 `~/BobWork/BobWorkspace` 抽样（标注「需实测量」处除外）。

## 0. TL;DR

- **现状不是"每轮全量重发"**：前端已实现「压缩游标跳过」（`compactedUntilRef`），游标之前的轮次不发送；但游标只在**离散折叠事件**（append 侧 R-25/26：15 轮或 ~100k token；route 侧 R-14：约 200k 字符且仅当节点有上游链时才触发）后推进。两次折叠之间，游标之后的所有历史轮次**每轮原样重发**（含每轮 assistant 的 reasoning 以 `<think>` 全文回填），这是 T2 要降的输入大头。
- **前缀缓存是硬约束**：请求缓存键 = `[system][tools][history]` + 尾部当前轮 user。任何「每轮在头部增删/改写早期轮」的做法都会从改动点起**整段 miss**；与缓存兼容的折叠只有两种形态：①离散折叠事件 + 折叠输出放到尾部（现网 C8 模式）；②服务端确定性裁剪（每轮输出同一字节序列，尾部增长）。
- **推荐落点**：**D（node 记忆摘要升级，append 侧滚动投影）+ C（route 内 projection hook，预算前瞻提前折叠）**。二者都只是"现网已存在的折叠设施（R-14-C / R-25/26）+ 触发策略 + 输入源切换"，不是新架构；**前端零改动**（游标/跳过/尾部注入机制已就绪）。
- **关键升级点**：把折叠的**输入源**从「request messages 里被裁的 Q/A 文本」切换为「.trajectory 事件日志派生」（`ConversationTurn.taskId` 已持久化到 .md，`appendPayloadFromEvents` / `deriveMessages` 已实现），使「模型面投影 = 日志派生的压缩记忆、真相 = append-only 日志」落地。
- 明确不做：前端发送前折叠 / 每轮窗口滑动（缓存结构性破坏，见 §4-A）、C8 缓存头策略改动、.md 对话记录删除、R-14 拒绝语义改动、新记忆存储格式、.trajectory GC、前端会话日志直连重构。

## 1. 现状数据：长会话 messages 典型构成（代码实读 + 抽样）

### 1.1 端到端请求链（每轮）

```
用户输入 → ChatNodeKernel.doSend
  ├─ baseMessages = [...messages(去 system), 新 userMsg]          # node.data.messages 全量内存态
  ├─ compactedSkip = min(compactedUntilRef×2, baseMessages.length-1)
  ├─ apiMessages  = [system(SYSTEM_PROMPT 常量), ...baseMessages.slice(compactedSkip)]   # ← 游标前不发
  ├─ 每条 assistant 消息：reasoning 全文以 <think> 回填进 content（ChatNodeKernel.tsx:3605-3608）
  ├─ 每条消息 attachments：folder →「操作目录」块；file →「附件列表+read_attachment 指引」内联
  ├─ fetchUpstreamContext()（上游 node 的 title+summary 索引表）prepend 到当前轮最后一条 user
  └─ POST /api/chat { messages, nodeId, forcedSkills[], enabledMcpIds[], ... }   # 技能/附件正文不在请求体

服务端 route.ts POST：
  messages 原样进入 → PDF Bridge → applyUpstreamNodeBridge（R-12 上游成果块全文 / R-17 祖先声明 /
      本节点成果块 + ## 压缩记忆 / R-14 超闸裁剪 + R-14-C 折叠 / 全部 prepend 到最后一条 user）
  → injectSkillContext（L1 目录 + forcedSkills L2 正文 → 尾部 user）
  → injectThinkingPrompt（BASE_SYSTEM_PROMPT 进 system；思考指令 → 尾部 user）
  → 项目路径/授权目录/偏好目录/OCR 事实/AI Coding 上下文 → 全部 prepend 尾部 user（C8）
  → 工具循环：每轮 chat.completions.create 携带 kctx.conversationMessages 全量重发 + loopToolDefs
```

### 1.2 前端每轮发送构成（必答 Q1）

- **messages 来源与增长**：`node.data.messages`（`ChatNodeKernel.tsx:946`）由画布恢复节点时从 .md 构建
  （`CanvasFlow.restoredNodeToFlowNode:292-317`：`.md` 对话记录每轮 → `user`+`assistant` 两条
  `ChatMessage`）；每轮 doSend 完成并流式结束后 `setMessages` 追加；持久化经 `POST /api/nodes append`
  把 (question, answer, reasoning, toolCalls, outputFiles, taskId) 写回节点 .md（`appendConversation`，
  .md 对话记录**只增不减**）。
- **是否全量**：非全量——`apiMessages` 经 `compactedSkip = min(compactedUntilRef×2, len-1)` 裁剪
  （`:3590-3593`）；`compactedUntilRef` 初始来自 `data.compactedUntil`（=.md `memory_compacted_until`，
  `:2039`），运行时只在 append 响应带 `compacted.new_compacted_until` 时推进（`:4457`）。**游标之后的
  全部轮次每轮原样重发**，直到下一次折叠事件。
- **systemContent**：前端恒为两行静态常量 `SYSTEM_PROMPT`（`:149-150`），**无记忆摘要注入 system**
  （注释 `:3560-3563` 明确：上游上下文曾放 system，因缓存头失效已挪到当前轮 user）。
- **node 记忆/压缩摘要在哪读取**：前端只读 `data.compactedUntil`（数字，决定跳过量）；记忆**正文**
  （`## 压缩记忆`、成果块）由**服务端** `loadNodeById` 读取并在 Node Bridge prepend 到当前轮 user
  （route.ts `:2126-2129` + `:2237-2244`）；前端 `fetchUpstreamContext`（`:2478`）仅经
  `GET /api/nodes?id=` 取上游 `title+summary` 构造索引表。
- **上游索引表 / 附件序列化 / 强制技能占位**：上游索引表 prepend 到当前轮最后一条 user（`:3647-3653`）；
  附件序列化见 `:3611-3637`（folder/file 两类，正文内联 + read_attachment 指引）；强制技能只发
  `requestBody.forcedSkills` 名字数组（`:3702-3704`），正文注入在服务端。
- **隐藏大头**：每条历史 assistant 的 **reasoning 全文以 `<think>` 回填**再发送（`:3605-3608`）；
  长思考会话里 reasoning 常远超正文，是"游标后历史"重发成本的主要来源之一。
- **特例**：续写（continuation / ask_user 补充）场景只发 4 条最小上下文（`:3580-3585`），不属长会话问题。

### 1.3 后端入口现状（必答 Q2）

- route 收到 messages 后**直接全量使用**（`messagesWithContext = messages`，`:2765-2766`），无独立窗口；
  唯一的消息级裁剪在 `applyUpstreamNodeBridge` 的 **R-14 闸**（`:2167-2231`）：字符总长（messages +
  注入）> `contextGateForContext(contextWindow)`（1M→200k 字符，下限 32k）时从头部成对丢弃
  user+assistant 至闸值 80%（保留 ≥2 轮 + 当前轮）。
- **R-14/R-14-C 触发点**：在 **chat 请求内**（Node Bridge，POST 内）；**但仅当节点有上游/祖先链时
  才进入**（`applyUpstreamNodeBridge` 早退 `:2107`）→ **孤立节点在 route 侧永远不裁剪**，长会话
  只靠 append 侧压缩。
- R-14-C（`compactTrimmedHistoryForCache`，`:2002-2080`）：被裁轮次 → `runCompaction` 增量合并进
  node `compressedMemory` + 推进 `memory_compacted_until`（写 .md frontmatter），冷却 10min 内降级
  硬事实直写；折叠输出 prepend 到**本轮最后一条 user**（不进 system，C8）。
- **nodes/compact.ts 增量压缩（R-25/26）在什么路径被调用**：`/api/nodes append`（nodes/route.ts
  `:447-546`）——每轮流式结束后前端调用 append 时触发：`shouldCompact`（R-26：`memory_compacted_until`
  之后未压缩文本 ≥ `compactTriggerTokensForContext`（1M→100k token≈125k 字符，下限 16k）或 ≥15 轮，
  token 触发受 10min 冷却压制，轮数触发不受冷却）→ `runCompaction`/`compactionFallbackSummary` →
  写回 `## 压缩记忆` + 游标，append 响应带 `compacted`，前端据此推进 `compactedUntilRef`。
- **与"messages 全量重发"的关系**：append 侧折叠 → 游标推进 → 前端下轮跳过 → 输入变小；
  route 侧 R-14 裁剪只作用于**本轮实际 prompt**（上传仍全量）。二者共享同一游标与 `runCompaction`
  设施，但触发点不同、时机不同（chat 请求内 vs append 后）。
- **发现的 gap（现状问题，T2 直接收益点）**：当 R-14-C 在 route 内先折叠并推进了 .md 游标后，
  同轮 append 侧的 R-26 判定会因"已被覆盖"（`newUntil <= compactedUntil`）而返回 `compacted=null`
  → **前端内存游标不推进** → 下一轮前端仍全量上传已被折叠的轮次（route 每轮重复确定性裁剪兜底，
  实际 prompt 不会超闸，但上传带宽与 route 重复劳动持续存在，直到 append 侧累计 15 轮再触发一次）。

### 1.4 真相 vs 模型面 现状分离（必答 Q3）

- **真相层（append-only）**：`.trajectory/<nodeId>/<taskId>.jsonl` 每轮一文件（route.ts `:4397/4418`
  `persistEventLog`），事件含 user 输入、assistant attempt/终答全文、tool_result 全文、compaction
  事件（`CORE_EVENT`，`event-log.ts`）；.md 对话记录（只增，Q/A + reasoning/toolCalls 的 RMETA 注释）。
- **投影层（模型面）**：现网唯一投影 = `## 压缩记忆`（五节：任务目标/已确认事实/当前争议/已排除路径/
  用户偏好，R-27 硬事实原文照抄）+ 成果块 + 摘要节——**只在折叠事件后存在**，且折叠输入是"被裁
  request 文本"，**不是日志派生**。
- **事件日志已可作投影源**：`ConversationTurn.taskId` 已持久化到 .md（每轮 → 日志文件）；读侧
  `readTrajectoryMessages` / `deriveMessages` / `appendPayloadFromEvents`（单轮 → question/answer/
  reasoning/toolCalls/outputFiles）已实现并用于 append 的 derive 分支（nodes/route.ts `:383-397`，
  含 0/250/700ms 短重试应对日志晚落盘）。**缺的是**：多轮跨文件汇总、把派生文本作为折叠输入的接线。
- **实测（2026-09-08 抽样）**：`~/BobWork/BobWorkspace` 非回收站 42 个节点 .md：轮数 max=9、
  mean=2.3、median=1、无 >15 轮样本；对话记录字符 max≈199.5k（9 轮）、198.2k（4 轮）——单轮可达
  ~50k 字符（附件/长文档全文问答）。**全部样本 `memory_compacted_until` 均为 0**（从未折叠）。
  结论：真实长会话以「大体积轮」为主而非「轮数多」，15 轮 turns 触发弱，token/字符触发与 R-14 超闸
  才是主路径；「典型构成」仍需实测量（活跃 sqlite 会话 + 逐轮 token 曲线，见 §6-验证门）。
- `.trajectory` 抽样：245 个 jsonl，mean 25.8KB / median 11.8KB / max 331KB（单轮 30-72 次工具调用）
  → 日志可作为派生源，但**工具结果全文体积大**，派生输入须只取 question/answer/reasoning，不可取
  全量 tool result（防压缩模型输入爆炸）。

### 1.5 前缀缓存基线（必答 Q4）

- 缓存键分段已显式建模（route.ts `:3130-3168`）：`prefixSegments = { system, tools, toolsByte,
  history, all }`；**history 段 = 除 system 外、除最后一条（当前轮）user 之外的全部消息**
  （`:3153-3156`）。system/tools 字节稳定、动态内容全部落在"最后一条 user"（C8）→ 每轮历史前缀命中。
- 系统提示字节 = 服务端 `BASE_SYSTEM_PROMPT`（agent 专属 base）+ 前端静态两行（`injectThinkingPrompt`
  `:1532-1544` 合并），与 tools 一样属于"常驻缓存头"。
- **安全/危险判定**：
  - 危险：把"每轮重派生的早期轮摘要"插在历史**头部**（system 之后）→ 摘要文本逐轮变 → history 段
    逐轮漂移 → 折叠点之后整段 miss；若再配合头部删轮（窗口滑动），等于**每轮从头 miss 全部历史**，
    命中部分计价优势全部丢失（DeepSeek 缓存读取价远低于 miss 价），净成本反升。
  - 危险：任何"逐轮把最老轮移出历史"（游标每轮 +1）→ 上一轮与下一轮的历史序列在首轮处即分歧 →
    除 system+tools 外每轮全 miss。**结论：'每轮折叠' 与 '前缀缓存' 在头部操作上结构性互斥。**
  - 安全（现网已证）：折叠只在**离散事件**发生（游标整体跳跃），两次折叠之间历史头字节不变、尾部长；
    折叠产物（压缩记忆）与上游/技能/偏好等动态内容一律 prepend 到**当前轮最后一条 user**
    （尾部必 miss 段）→ 不破坏缓存头；服务端确定性裁剪（同一输入 → 同一裁剪结果 + 尾部长）也安全。
  - 注入位置统一在尾部还有一个好处：压缩记忆在折叠轮被写进"本轮 user"，该轮冻结为历史后其字节不变，
    后续轮的历史段指纹稳定（仅尾部新增）。

## 2. 候选落点对比

> 四案均以"游标 + 尾部注入 + 离散折叠"为兼容前提讨论；凡含"每轮头部折叠"语义的变体已在 1.5 判定为
> 缓存破坏，不列为推荐，只作对照。

| 维度 | A. 前端发送前折叠 | B. 后端入口投影（Node Bridge 前） | C. 路由内每轮 projection hook（Node Bridge / R-14 旁） | D. node 记忆摘要升级（append 侧滚动投影） |
|---|---|---|---|---|
| **做法** | doSend 里对游标后的早期轮再折叠（窗口/摘要）后发送 | POST 收 messages 后、Node Bridge 前，把早期轮替换为投影文本 | 扩展现有 R-14-C：触发条件从"超闸才裁"改为"预算前瞻/轮数提前"，折叠输入切日志派生；hook 提到 chain 判断之外 | R-25/26 触发参数可配 + 折叠输入源切为日志派生 + 触发频率提升（每轮滚动/低频），游标与注入点不动 |
| **改动面** | ChatNodeKernel + 新协议（前端拿不到记忆正文：GET /api/nodes list 无 compressedMemory 字段，也读不到 .trajectory） | route POST 开头一段；需与 Node Bridge/skills/think 的注入顺序理清 | route `applyUpstreamNodeBridge` 裁剪段 + 共享纯函数；含孤立节点路径 | nodes/route append 段 + compact.ts 参数化；纯后端 |
| **前缀缓存影响** | 每轮头部折叠/删轮 → history 段每轮漂移 → **每轮全量 miss**；最差案 | 若投影每轮重派生并放头部 → 同 A 全 miss；若复用 .md 持久化记忆 + 离散折叠 + 尾部注入 → 与现网一致（安全） | 折叠事件离散、产物尾部注入 → 与现网 R-14-C 完全同构（安全）；提前折叠使"折叠 miss"发生得更早但每次代价更小 | 与现网 R-25/26 完全同构（安全）：折叠轮整段 miss 一次（现状已接受），轮间稳定；触发频率上调 → 折叠 miss 次数增加，需参数护栏 |
| **行为风险** | 双轨折叠（前端/服务端）状态一致性；摘要质量下降时早期细节不可再取；每轮多一跳 | 与 R-14-C 折叠逻辑重叠易双轨；位置在技能注入前，折叠文本会把技能/思考指令裹进记忆（错误） | 压缩模型调用次数上升（延迟/成本）；与 append 侧双触发点并发写 .md（需保留"写回前重读节点"模式） | 同上：append 是同步 await，每轮触发会拖慢轮结束；游标推进必须同步落盘、记忆文本可异步，存在"下轮注入旧记忆"中间态（cover-check 可兜） |
| **与 R-14 / 事件日志关系** | 绕过现有设施，与 R-14-C/R-25/26 并列第三套 | 平行于 R-14-C；日志可作为输入源 | 直接扩展 R-14-C，复用 extractTrimmedTurns/runCompaction/COMPACTION 事件/cover-check | 直接扩展 R-25/26；`ConversationTurn.taskId` 已提供日志回溯锚点，`appendPayloadFromEvents` 现成 |
| **实施量** | 大（协议 + 前端 + 双轨一致性） | 中-大 | 中 | 小-中 |

### 逐案简评

- **A（前端折叠）**：结构上最差——①前端既无记忆正文也无日志访问，必须新增 API/字段；②每轮在头部动历史
  与前缀缓存互斥（1.5）；③与 .md 游标双写一致性问题。**否决**，仅保留"前端预判压缩提示"这类展示逻辑。
- **B（入口投影）**：位置过早，会把技能/思考/偏好注入裹进"被投影的早期轮文本"造成记忆污染，且与
  R-14-C 重叠成双轨。不推荐独立落地；其合理内核（"不等超闸、在请求内提前折叠、孤立节点也生效"）并入 C。
- **C（route projection hook）**：把"只在超闸才裁（且要有上游链）"升级为"预算前瞻（未压缩量接近闸值
  即提前折叠一轮）+ 孤立节点同样生效"，输入源切日志派生。收益：实际裁剪与游标推进同步，消除 1.3 的 gap；
  每轮 prompt 提前变小。风险集中在压缩模型调用频率与并发写 .md。
- **D（append 侧记忆升级）**：收益路径最短——append 每轮必经、零前端、游标语义现成；把触发从
  "15 轮 / 100k token 的一次性大折叠"细化为"更早/更平滑的多次小折叠"，并把折叠输入从 .md 文本切为
  **事件日志派生**，即完成"模型面=日志派生的精简投影"。是 MVP 首选；频率上限受压缩调用成本与冷却约束。

## 3. 推荐落点 + MVP

### 3.1 推荐

**主落点 D：node 记忆摘要升级**（append 侧滚动投影）——触发策略参数化 + 折叠输入源切换为
.trajectory 事件日志派生 + 频率提升（离散、非每轮），投影写入/注入/游标/前端跳过全部沿用现网机制。
**加速项 C：route 内 projection hook**——R-14-C 触发从"超闸才裁"升级为"预算前瞻提前折叠"并把 hook
提到 chain 判断之外（孤立节点同样受益），使服务端实际裁剪与游标推进同步（修 1.3 gap）。

理由：
1. 全部设施现成（R-25/26、R-14/R-14-C、shouldCompact/runCompaction/extractHardFacts/
   compactionFallbackSummary/COMPACTION 事件/前端 compactedUntilRef 跳过/尾部注入 C8），T2 只是
   **触发策略 + 输入源**升级，不是新架构；
2. 前缀缓存硬约束下（1.5），唯一与缓存兼容的形态就是现网这套"离散折叠 + 尾部注入"——所以不做前端
   折叠新路径；
3. "真相 vs 模型面"分离由此真正落地：折叠输入 = `readEventLog(.trajectory/<node>/<taskId>.jsonl)`
   → `appendPayloadFromEvents` 派生（回退 .md 文本），模型面 = 日志派生的压缩记忆，真相 = append-only
   日志 + .md 对话记录（不删）；
4. 前端零改动，MVP 可纯后端完成，行为回归面小。

### 3.2 MVP 步骤（最小可行）

1. **触发策略纯函数**（compact.ts）：`shouldCompact` 参数化 + 新增"预算前瞻"判定
   （未压缩 token ≥ contextWindow×X%（如 8-10%）或未压缩轮数 ≥ K（可配，如 6-8），token 触发沿用冷却）。
   单测覆盖（现有 compact.test.ts 扩展）。
2. **折叠输入源切换（D）**：nodes/route append 段，range 内每轮若有 `taskId` → 读该轮 .trajectory
   日志 → `appendPayloadFromEvents` 派生出 {question, answer, reasoning, toolNames} 的精简文本作为
   `uncompressedTurns`（**只取 Q/A/reasoning，不取 tool result 全文**）；日志缺失/晚落盘 → 沿用
   0/250/700ms 短重试（derive 分支同款）→ 仍缺回退 .md 文本。
3. **预算前瞻折叠（C）**：route `applyUpstreamNodeBridge` 裁剪段把触发从"总长 > 闸值"扩为"总长 > 闸值
   或 未压缩量达前瞻阈值"，hook 提到 chain 判断之外；折叠输入与步骤 2 共用同一派生函数；R-14-C 的
   cover-check/冷却/写回前重读保持不变。
4. **游标传播不变量**：游标推进（frontmatter）必须同步落盘并随 append 响应返回（现网机制），
   保证前端下轮 skip 生效；压缩记忆正文生成允许异步/冷却，中间态由 cover-check 兜底。
5. **遥测**：COMPACTION 事件沿用（shadowedTurns/hardFacts/compactedUntil）；可选在 context_meter /
   done 事件补"折叠前预估输入 vs 折叠后实际输入"。

### 3.3 验证门（before/after 量化）

1. **量化基线（before）**：选 1-2 条真实长会话（≥15 轮或单轮大体积、接近闸值），逐轮记录
   `context_meter`（system/tools/conversation/capacity）与 `done` 事件 usage
   （promptTokens / cacheHitTokens / cacheMissTokens / hitRate，route 已落盘）→ 得
   "每轮输入 token + 命中率 + R-14 裁剪次数 + append 端到端延迟"基线。
2. **量化对照（after）**：同会话复跑，对照指标：①每轮 prompt tokens 下降 %（目标不预设，报告实测）；
   ②hitRate 稳态不塌（护栏：折叠后稳态命中率低于基线 N% 或连续折叠 miss 代价 > 节省 → 回退参数）；
   ③`prefixSegments.{system,tools}` 全程零漂移、`history` 仅折叠轮变化（≤1 次/折叠）；
   ④折叠模型调用增量次数与成本 < 输入节省。
3. **质量保全（旧轮细节可再取）**：折叠后追问早期轮具体事实（金额/日期/条款号/当事人）→ 模型能直接答
   出硬事实（R-27 原文照抄断言）或调用 intern_search/read_manifest 取回正确原文（冒烟用例）；.md
   对话记录与 .trajectory 日志须仍可读（真相未删）。
4. **回归**：tsc 0 / 201+ 单测（compact、context-limits、node-markdown、trajectory）/ lint 新增 0；
   T1 冒烟集复跑（压缩触发、read_file 续读、长文档工具结果不退化）。

### 3.4 风险清单

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 折叠频率上调 → 折叠点 miss 总代价 > 省下的输入 token（缓存价差倒挂） | 参数护栏 + 验证门 2 的稳态 hitRate 下限；默认保守起步（K=6-8 轮）逐步收紧 |
| R2 | 压缩模型调用成本/延迟（append 同步 await） | 冷却保留（轮数触发不受冷却 + token 触发冷却）；必要时记忆文本生成异步化，游标同步推进 |
| R3 | 日志缺失/晚落盘/被 GC → 派生输入不完整 | derive 分支现成的短重试 + .md 文本回退（回退安全，行为 = 现网） |

## 4. 明确"不做"范围（避免与 R-14 / 前端会话重构重复）

1. **不做前端发送前折叠 / 不做每轮窗口滑动**——与 DeepSeek 前缀缓存结构性互斥（§1.5），且前端无记忆
   正文/日志访问，需新协议；若确有 UI 侧诉求，只做"压缩进行中提示"这类展示（现网已有）。
2. **不改 C8 缓存头策略**：system 继续只含字节稳定 BASE_SYSTEM_PROMPT；动态内容（含任何新投影）一律
   尾部 user 注入；不动 prefixSegments 语义。
3. **不重做 R-14 语义**：保留"上游注入独占超限 → 拒绝并提示拆分"与"至少保留最近 2 轮+当前轮"；
   只扩展触发时机与输入源。
4. **不删除 .md 对话记录全文**：压缩只影响"模型面"（发送/注入），.md 与 .trajectory 始终是真相与
   可再取源；intern_search/read_manifest/read_upstream_node 检索链路不动。
5. **不引入新记忆存储格式**：沿用 frontmatter 游标 + `## 压缩记忆` 五节结构 + COMPACTION 事件；
   避免第三套折叠实现。
6. **不做 .trajectory GC/保留策略、不做前端会话日志直连重构（P2 级"消息由事件流渲染"）**：前者另立项，
   后者属更大范围的 DSH 会话面改造，T2 仅消费既有日志。
7. **不改前端续写（continuation）最小上下文路径**；eventsToTraceWindow/轨迹窗口属前端 trace 展示，
   与本方案无关。
