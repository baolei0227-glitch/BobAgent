# bob-bank-statement · 输出格式规范 v1

> 目的：让 Skill 脚本（`scripts/run_statement_pipeline.ts`）、Agent 三态朗读话术、人工复核清单生成器、事实舱写入器四方，对"同一批数据怎么导出/解析"有一致理解。
> 任何一方修改了实际实现，都要反向更新本文件。

---

## 0. 总览 · 三类文件

输入：`/abs/path/to/xxx.pdf`（或 `.png/.jpg/...`）

输出目录（`--out_dir`，默认 `projects/homework/`）下生成三份文件：

| 产物 | 文件名模式 | 生成档 |
| --- | --- | --- |
| Excel 三 Sheet（四 Sheet if forensic） | `${stem}_流水明细.xlsx` | standard / forensic |
| Markdown 勾稽报告 | `${stem}_勾稽报告.md` | standard / forensic |
| JSON 状态摘要 | `${stem}_状态.json` | **任何档都有**（含 quick） |

其中 `${stem} = basename(input, ext)` 做一次安全字符替换：`[^w.-]+ → _`。

---

## 1. 状态 JSON · `${stem}_状态.json` Schema

```ts
interface StatementJobStatus {
  ok: true;
  exitCode: 0;
  detectedAsLedger: boolean;                // 是否判定为银行流水
  passRate: number | null;                  // passedRows / comparableRows（0..1）；detectedAsLedger=false 时 null
  coverageRate: number;                     // comparableRows / totalRows（0..1）
  longestPassingChain: number;              // 最长连续勾稽通过链长度
  crossPageStatus:                          // 跨页余额衔接
    'pass' | 'fail' | 'needs_review' |
    'not_checked' | 'insufficient_data';
  semanticsStatus: 'confirmed' | 'inferred' | 'ambiguous';
  issuesCount: number;                      // report.issues.length
  status: 'green' | 'yellow' | 'red';       // 三态分档（见 SKILL.md §三）
  statusText: string;                       // 同三态话术，Agent 直接读
  mode: 'quick' | 'standard' | 'forensic';
  scenario: 'per_page' | 'whole_doc';
  glmPriority: 'none' | 'optional' | 'force';
  inputPath: string;                        // 原始输入的绝对路径
  pageCount: number;
  ocrMethod: 'pdf-text' | 'vision-ocr' | 'glm-ocr';
  upgradedCount: number;
  outputExcelPath: string | null;           // standard/forensic 才有；quick 为 null
  outputMarkdownPath: string | null;        // standard/forensic 才有；quick 为 null
  statusJsonPath: string;                   // 本 JSON 文件的绝对路径
  exportAt: string;                         // ISO 时间（YYYY-MM-DDTHH:mm:ss，本地时区）
}
```

Agent **首先**读：
1. `detectedAsLedger`：若 `false` → 直接走 `RED 非流水信号` 话术，别继续读勾稽结论；
2. `status` + `statusText`：Agent 朗读 `statusText`，**不要**自己重新拼话术。

## 2. Excel · `${stem}_流水明细.xlsx` 三 Sheet 结构

### Sheet 1：交易明细（Main Table）

列顺序：

**单列金额模式（四列表头 日期·摘要·金额·余额）**：

| # | 列名 | 来源字段 | 备注 |
| --- | --- | --- | --- |
| A | 序号 | `rowGlobal` | 跨页连号 1-based；单页时退化为 `rowPage1Based` |
| B | 页码 | `pageIndex0Based + 1` | 1-based |
| C | 页内行号 | `rowPage1Based` | 1-based（对齐 `report.issues[i].row`） |
| D | 日期 | `dateText` | 原文（准入后：red cell 已清空为 `""`） |
| E | 摘要 | `summaryText` | 原文 |
| F | 金额 | `amountText` | 原文：可能有逗号、¥、`(1,234.00)` 括号负数等 |
| G | 余额 | `balanceText` | 原文 |
| H | 金额·元 | `fmtYuan(amountCent)` | 规范为 `¥1,234.56` 千分位；空串 = null |
| I | 余额·元 | `fmtYuan(balanceCent)` | 同上 |
| J | 行类型 | `kind` | 枚举同 `StatementRowKind`：`transaction / opening_balance / closing_balance / control_subtotal / control_total / header_repeat / separator / noise` |
| K | 参与勾稽 | `participatesInReconciliation ? "是" : "否"` | 仅 transaction 行且被控制行政策选中的才是"是" |
| L | 颜色 | `finalColor` | green/yellow/red；空串 = 未做逐格评估（coordinate_text 页等） |

**双列收入支出模式（五列表头 日期·摘要·收入·支出·余额）**：

F/G 扩展成 `收入/支出` 两列，H/I 从 `金额·元/余额·元` 扩展成 `收入·元/支出·元/余额·元`，其余列相同。脚本从 `markdownHeader.length === 5` 自动判定。

行筛选（交易明细只保留"人看的主数据"）：
- `participatesInReconciliation === true` 的行（普通交易行）；
- `kind ∈ {opening_balance, closing_balance}`：余额锚点；
- 不保留：`header_repeat / separator / noise / subtotal / total` → 去「控制行明细」Sheet 看。

### Sheet 2：控制行明细（Control & Metadata Rows）

同交易明细的列顺序；行集合 = 所有行 **减去** `transaction + opening/closing（已去 Sheet1）`：
- 上半部分：`subtotal / total` → 用于核对银行方"本页合计/本年累计"；
- 下半部分：`header_repeat / separator / noise` → 噪音分布可以帮人工判断"是不是扫描件乱码页"。

### Sheet 3：勾稽异常清单（Issue Log）

| 列 | 含义 |
| --- | --- |
| 页码 | `pageIndex0Based + 1`，issue 没绑定 row 时 = -1 + 1 = 0 |
| 行号(页内) | `issue.row`（1-based，对齐 Sheet1.C「页内行号」） |
| 全局序号 | 命中行的 `rowGlobal`；若行未落在 rowsByKind 返回 null |
| issue.kind | `row_mismatch / amount_parse / balance_parse / date_parse / cross_page / ...`（与 `LedgerIssue['kind']` 一致） |
| issue.message | 原文（带 "[Page X]" 前缀） |
| 原始四列：日期/摘要/金额/余额 | 从 rowsByKind 拼 `"${date} | ${summary} | ${amount | income/expense} | ${balance}"`，方便肉眼对照 |

注意：`issues.length > 0` 并不自动代表 red 档；只有「很多行硬冲突 + passRate 低」才会进 red。

### Sheet 4（仅 `--mode=forensic`）：逐格评估明细

每行对应一个 `CellVerification`：

| key | row | 列 | visual | structural | normalization | reconciliation | human | finalColor |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

- key 格式：单页报告 `R{row}_{KIND}`（如 `R12_AMOUNT`）；多页报告 `P{n}_{key}`（如 `P3_R2_BALANCE`）；
- finalColor = 内联 `aggregateColor()`：任一最差维触发 red/yellow → 行级红绿灯，便于筛选。
- 典型用途：筛选 `finalColor=red` 做人工复核清单。

## 3. Markdown 报告 · `${stem}_勾稽报告.md` 三段模板

结构固定为三节，顺序不能改（Agent / 后续解析器都按节标题定位）：

### §1 三态结论

第一行直接写 Emoji + 状态：
```
# 银行流水勾稽报告 · 🟢GREEN
# 银行流水勾稽报告 · 🟡YELLOW
# 银行流水勾稽报告 · 🔴RED
```

然后写 `statusText` 原句（不要加 Agent 自己的解释，也不要改写数字——避免跟状态 JSON 里数值漂移）。

### §2 Summary 汇总表

固定 12 行指标（**顺序不要变**，自动化比对依赖）：

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| detectedAsLedger | true/false | 判定为银行流水 = true |
| comparableRows | N | 可读可比较行数 |
| passedRows | N | 勾稽一致 |
| failedRows | N | 勾稽不平 |
| insufficientRows | N | 数据不全不可校验 |
| passRate | N% | passed/comparable；< 50% red |
| coverageRate | N% | comparable/totalRows；< 40% red |
| longestPassingChain | N | 连续通过链；≥ 10 才能 green |
| crossPageStatus | pass/fail/needs_review/not_checked/insufficient_data | 跨页余额衔接 |
| semanticsStatus | confirmed/inferred/ambiguous | 账务语义确认 |
| issuesCount | N | 所有 issues 合计 |
| 三态结论 | GREEN/YELLOW/RED + 说明 | 与 SKILL.md 三态话术一致 |

### §3 交易样本（前 200 行）

- 直接写 Markdown 表格：表头 = `markdownHeader`（四列或五列）；
- 只过滤 `header_repeat / separator / noise`，保留 opening/closing；
- 超过 200 行时在末尾提示：`_（共 N 行，此处截断前 200 行；完整明细见 Excel）_`；
- **0 行时**输出一句：`_（无可展示行：本文件未被识别为银行流水，或行聚类后无有效交易行）_`。

可选 §4 勾稽异常摘录（issues.length > 0 时出现）：前 30 条 `issue.message` 用 `- ` 无序列表。

文末固定 footer：
```
---
_本报告仅基于 OCR 结果的数值自洽性生成，不构成法律定性；Green 档不等于"原件真实"，Red 档不等于"伪造"。红色档不得进绿色事实舱。_
```

## 4. 三态分档规则（Single Source of Truth）

脚本 `classifyStatus()` 作为唯一实现，所有其它地方不要重写，保持同步：

```ts
if (!detectedAsLedger) → RED
if (passRate < 0.50 || coverageRate < 0.40) → RED
if (passRate >= 0.98 && coverageRate >= 0.95 && longestPassingChain >= 10 && crossPage ∈ {pass,not_checked}) → GREEN
else → YELLOW
```

边界情况：
- `detectedAsLedger=false` 但 `comparableRows` 很小：仍 RED（非流水信号）；
- `passRate=null`（comparableRows=0）视为 `passRate=0` → RED；
- 单页 PDF `crossPageStatus=not_checked`：视为通过（绿色准入允许）。

## 5. 双列金额模式（income_expense_columns）自动扩列

当 `report.markdownHeader.length === 5`，或「`semantics.amountMode === 'income_expense_columns'` 且 classifyStatementRows 解析到 incomeCent/expenseCent」即判定为双列模式：

- Excel / Markdown 的表头从 `[日期, 摘要, 金额, 余额]` 扩到 `[日期, 摘要, 收入, 支出, 余额]`；
- `金额·元` 列替换成 `收入·元 / 支出·元` 两列；
- `StatementLedgerRow.amountCent` 此时为 null，**绝对**不能把 `incomeCent - expenseCent` 合成 amountCent 再写（否则会污染"同一行到底是哪种列定义"的可回溯性）。

脚本按 `markdownHeader.length === 5` 判断即可，不需要自己看 semantics。

## 6. 颜色字段（finalColor）的含义

`finalColor` 来自 `worstColor([ R{row}_DATE, R{row}_SUMMARY, R{row}_AMOUNT, R{row}_BALANCE ])`，
每个 cell 的颜色由 `aggregateColor()` 五维合成：

| 维度 | red 触发 | yellow 触发 | green |
| --- | --- | --- | --- |
| visual | `unreadable` | `ambiguous` | `confirmed / verified_from_pdf / matched` |
| structural | `unassigned` | `ambiguous` | `assigned` |
| normalization | `invalid` | `ambiguous` | `valid` |
| reconciliation | `fail` | `insufficient_data` | `pass / not_applicable` |
| human | `rejected / unreadable` | `unreviewed / confirmed_from_image` | `confirmed` |

应用：
- 勾稽异常清单：若 `finalColor=red` 且 `passRate 不太低` → 优先怀疑 OCR 错值（先重识别，再怀疑银行流水本身）；
- 若 `finalColor=green` 但 reconciliation=fail → 才是真正的硬冲突。
