# Butler 公众号检索 · 评测

这套东西只回答一个问题：**「Search WeChat Articles」到底准不准**——在它之前，这条链路
（搜狗召回 12 篇 → LLM 精选 3 篇 → 读正文 → 综述 → CoVe 校验）一个指标都没有，
任何 prompt / 模型改动都只能靠感觉。

```
capture（建 pool）  →  export-labels  →  【人工填 grade / asserted】  →  score
 只调搜狗通道            铺出 12 篇 + 39 篇          10–20 分钟                出数字
 不经模型不落库          "生产没召回"的候选
```

## 快速开始

```bash
cd projects

# 1) 现状：读已落库的账本，出描述性统计 + 误杀复查队列（零成本、零配置）
pnpm tsx scripts/eval-wechat-search.ts stats

# 2) 建 pool：把同一个问题拆成几个检索方向各抓一次（只调搜狗通道，不经模型、不落库）
pnpm tsx scripts/eval-wechat-search.ts capture --via bridge \
  --query "<原句>" --also "<检索方向2>" --also "<检索方向3>"

# 3) 建 golden 骨架：生产看到的 12 篇 + 只有 pool 看到的那些
pnpm tsx scripts/eval-wechat-search.ts export-labels --runs .eval/runs --item <条目id>

# 4) 人工：打开 scripts/eval/golden.wechat-search.triage.md
#    ① 生产看到的 12 篇 → 填 grade；② pool-only 的 → 有价值的补 "asserted": true

# 5) 打分：通道召回 / precision@3 / 误杀率 / pool 覆盖
pnpm tsx scripts/eval-wechat-search.ts score --runs .eval/runs
```

`scripts/eval/golden.wechat-search.json` **要提交**（人工标注是最贵的资产）；
`.eval/` 下的报告与 run **不提交**（已在 .gitignore）。

## 三条口径（改动前先读）

### ① 召回只能在 pool 内测

没有"整个微信"的 oracle，所以"召回了 80%"这种话没有 pool 就是无意义的。诚实的口径只有一条：

> 人工**确认真实存在**（标签 `asserted: true`）的文章里，有多少真的进了召回。

未标 `asserted` 的标签只用于评价精选（precision / 误杀），**不进召回分母**——
否则"我随手写的期望"会被算成"系统漏召"。

生产链路一轮只留 12 篇，所以 pool 天然很窄。要扩大 pool 就把同一个问题拆成几个检索方向各抓一次：

```bash
# 只调搜狗通道（不经模型、不落库）；pool run 靠 itemQuery 归到原句，query 是子方向
pnpm tsx scripts/eval-wechat-search.ts capture --via bridge \
  --query "债权人垫付诉讼费 劣后债权人" --also "破产衍生诉讼 诉讼费 缓交" --also "破产 劣后债权 清偿顺序"
pnpm tsx scripts/eval-wechat-search.ts score --runs .eval/runs
```

**`export-labels` 会把"生产没召回"的 pool 候选也铺进 golden**（清单里的 ② 段）——
不标它们，召回率就没有分母。不用全标：只给"本该被搜到"的补 `asserted: true`，
其余留 `null`（留空不进任何分母，不会污染指标）。

### ② 误杀率是和 precision 同等重要的指标

精选的上游是 12 篇的窄召回，**判掉一篇人工认为相关的，用户可能永远看不到它**。
所以报告里 `误杀率`（dropped 中 grade≥2 的占比）与 `precision@k` 并列，误杀明细直接列在报告里。

### ③ nDCG 只在有模型排序时才算（2026-10-01 起账本会带 `rank`）

落库账本（`ChatMessage.searchTrace`）按**召回下标**排列 —— 这是为了前端分组能对上号。
模型的相关度顺序**单独记在 `WechatSearchTraceItem.rank`**（0 = 最相关），
所以从这一版起，新落库的轮次都能**离线**算 nDCG，不必再靠 `capture --via server` 现抓。

两条边界（都由测试钉住）：
- **兜底路径不写 rank**：模型不可用时那 3 篇是"取召回前 3 篇"，顺序是召回序，
  给它标名次等于凭空造一份模型排序 → 宁可不写，评测据此判回 `N/A`；
- **只标了部分 kept 也不写**：缺一个就判为无排序，不报残缺的 nDCG。

⚠ 引入字段**之前**落库的历史轮次仍然算不了 nDCG（字段是后加的，补不回来）——
你库里那条就是这种，重跑一次检索才会带上。

### ④ 去重按**标题**，不按 URL（2026-10-01 实测）

搜狗返回的是 `/link?url=…` **加密跳转链接**，同一篇文章在不同时间、不同检索方向会拿到
**不同的 token**。实测一个真实问题：

```
候选总数 62 条 · 唯一 url 62 个 · 唯一标题 51 个
生产那一轮的 12 篇里，有 7 篇的标题就在 pool 里，而两边 url 的交集 = 0
```

所以 `candidateKey` 以归一化标题为主键、url 只做兜底。代价写在测试里：
标题相同但确实是两篇不同文章的会被并成一篇（对这个大量转载的通道是可接受的取舍）。
真正的修法是**读正文后记 canonical URL**（`mp.weixin.qq.com/...`）——那只有读过正文才拿得到。

## rerank 二阶段精排：实测**不可用**（2026-10-01）

`scripts/eval-rerank-ab.ts` 拿真实 pool 做了 4 臂 A/B（基线 / rerank 全接管 / rerank 选 12 再由 LLM 挑 3 /
不设 12 篇预算的上限），**结论是方案本身被数据否掉了**，而且否掉的方式很值得记：

| 实测 | 值 |
|---|---|
| 51 篇候选的 rerank 分数 | **全部 1.0000**（极差 0.0000） |
| 8 篇（4 相关 + 4 无关） | 7 篇 1.0000、1 篇 0.9964（极差 0.0036） |
| 4 篇（2 相关 + 2 无关） | 同上 —— 只能挑出"跑步鞋"这种彻底跑题的，**同领域内不区分** |

**为什么这是最危险的一类故障**：分数全等 → 排序 = 输入原序 → 第一版实验因此得出
"rerank 把相关召回从 5/32 提到 7/32（+40%）"的**假象**（B 与 D 臂都是 7/32，看着还挺自洽）。
真相是那 7 篇只是 pool 的前 12 篇。所以：

- `src/lib/ai/rerank.ts` 里加了 `isDegenerateScores()`（极差 < 0.01 即判定退化）；
- A/B 脚本在退化时**拒绝解释 rerank 臂**，并把这个教训写在告警里；
- 顺带查到 `presets.ts` 里 glm 的 `rerank-3` / `rerank-plus` **在智谱侧不存在**
  （HTTP 400 `1211 模型不存在`），唯一可用的是 `rerank` —— 而它不可用。

**与 rerank 无关、因而仍然成立的发现**（都基于暂定标注）：

| 项 | 值 |
|---|---|
| pool 的相关率 | 62.7%（32/51） |
| **生产那一轮 12 篇的相关率** | **41.7%（5/12）** —— 比"从 pool 随机抽 12 篇"（期望 7.53 篇 / 62.7%）**还差** |
| 生产那一轮 precision@3 | 100%（3/3） |
| 12 篇预算把相关文章挡在门外的比例 | 相关召回 = 15.6%（5/32） |

也就是说：**瓶颈在"选出哪 12 篇"，不在"从 12 篇里挑 3 篇"**。LLM 精选那一步（precision 100%）没问题；
问题出在 12 篇这个召回集本身——它甚至不如随机。这与"去重失效白占名额"那个 bug 指向同一处。

## 候选宽度 / 精选 prompt 的 A/B：**一次否掉、一次打中**（2026-10-01）

`scripts/eval-width-ab.ts`（暂定标注，`--refresh` 重调模型）：

**实验一 · 候选宽度**（把候选从 12 加到 20/32/51，同一 prompt）

| 臂 | 候选数 | precision@3 | 必找命中(grade3) | nDCG |
|---|---|---|---|---|
| stored-0（生产现状） | 12 | 100% | 2/3 | N/A |
| N=12 / N=20 / N=32 / N=51 | 12 / 20 / 32 / 51 | 100% × 4 | **2/3 · 2/8 · 2/12 · 2/13** | 86.6% → 73.2% |

结论：**放宽候选宽度对 precision 无损，但不提升最终 3 篇** —— 精选在四个宽度下都坚持选那篇
grade=2 的实务随笔，必找命中恒为 2。所以"加宽召回"不是那个杠杆（我上一轮的猜想被否掉第二次）。

**实验二 · 精选 prompt**（固定候选，只加一段「一手优先」）

| 臂 | 候选数 | precision@3 | 必找命中 | nDCG |
|---|---|---|---|---|
| stored-0（生产现状） | 12 | 100% | 2/3 | N/A |
| P·current（现状 prompt） | 51 | 100% | 2/3 | 73.2% |
| **P·authority@生产12（同一批 12 篇，只换 prompt）** | 12 | **100%** | **3/3** | **100.0%** |
| P·authority（51 篇） | 51 | **100%** | **3/3** | **100.0%** |

`P·authority@生产12` 挑出的第一篇正是**「高院发布:关于破产衍生诉讼案件诉讼费缓交相关问题的通知」**
—— 生产原来判掉的那条权威一手来源（也是本工单第一轮就标记为"可疑误杀"的那条）。

**所以修复落成一行 prompt**（`enrich/route.ts` 的 `CURATE_SYSTEM` 加「补充要求（一手优先）」），
零成本、不必动 `MERGE_CAP`、不必接 rerank。

> ⚠ **方法论警告（必须记住）**：prompt 变体是我设计的，grade 也是我打的 —— 存在"教考一致"的风险。
> 减轻这一点的事实：那条被救回的权威通知，是在**设计 prompt 之前**、纯看账本就标记为可疑误杀的。
> 但最终仍需你填完 golden 后复核。

> ⚠ 顺带修掉一个**评测自身的 bug**：`ndcgAtK` 原先假定调用方把"理想序"排好了，
> 而 `scoreRound` 传的是 pool 原始序 → IDCG 被算小 → nDCG 虚高甚至 **144.9%**。
> 现在函数内部自己降序，并有单测钉住"≤1"。

## 规划器 prompt 的 A/B：**病根已修**（2026-10-01）

针对上一条的"规划器只产主题词方向"，`scripts/eval-plan-ab.ts` 用**完全相同的下游**
（搜狗扇出 + 轮转合并 + 12 篇预算）比四种规划 prompt，数同一件事：**这 12 篇里有多少"必找"**。

| 变体 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| base（现状） | **0** | **0** |
| doc（要求"含一个文书名型方向"，但用泛称） | **0** | **0** |
| docname（要求写出**文书正式名称**） | **3** | **2** |
| **PROD（改后生产源码原文）** | **2** | **2** |

两个非平凡的发现：

1. **"要求一个文书名方向"不够，必须要求写出文书的正式名称。**
   `doc` 变体产出的是「最高人民法院 夫妻共同债务 司法解释」（主题词 + 泛称"司法解释"）→ 捞回来的仍是解读；
   `docname` 产出「最高人民法院 关于审理涉及夫妻债务纠纷案件适用法律有关问题的解释」→ 直接带回原文（位置 0–2）。
2. **深度是无关变量**（此前我猜"每方向只取 6 条把官方文件截掉了"是错的）：
   4 个方向 + 上限 12 时，轮转只取每方向的**前 3 条**，所以 perQuery 4/6/8/10 的合并结果完全一样
   （实测都是 10 相关 / 3 必找）。深度只在**方向数很少**时才影响结果（1 个方向：6→10）。

已落到生产：`wechat-search/route.ts` 的 `PLAN_SYSTEM` 加了一条硬规则，**带"不许编造文书名"的护栏**
（想不起名称就退回主题词，不能瞎编 —— 编出来的名字会像 `民法典1064条` 那样返回 0 篇）。

> ⚠ **端到端复验踩到的坑（值得记）**：改完源码直连应用 `GET /api/butler/wechat-search` 复验，
> 两次仍然只给主题词方向、必找 0 —— 一度以为 prompt 没生效。
> 把**生产源码那段原文**抽进实验脚本再跑，两轮都是必找 2 → 结论是**跑在 8321 上的服务还在用旧代码**（没热重载），
> 不是 prompt 的问题。教训：**验证线上行为时，先确认线上跑的是不是你以为的那份代码。**

## 第三个查询（婚姻家事）：找到了**真正的病根**（2026-10-01）

q3：*夫妻一方以个人名义对外借款，出借人能否要求另一方共同偿还？举证责任如何分配？*

这一轮走的是**真实生产链路的一半**：直接调应用的 `GET /api/butler/wechat-search`
（规划器 + 搜狗扇出 + 轮转合并），**它不落库**，所以拿到了真实的规划方向与真实的 12 篇召回，
而不用写进用户的「小微」会话。

规划器给的方向（全是"主题词"型）：
`夫妻一方个人名义借款 共同偿还` / `夫妻共同债务 举证责任分配` / `个人名义借款 配偶还款责任`

| 观察 | 数字 |
|---|---|
| 真实召回 12 篇里的相关文章 | **10/12（83%）** —— 远好于 q1 那轮的 5/12（41.7%） |
| 真实召回 12 篇里的**必找**（一手/权威） | **0/12** |

即：**相关性修好了（轮转 + 标题去重生效），但 12 篇里一篇权威一手来源都没有。**

### 归因：一手来源住在另一个查询空间里

`directions --runs .eval/runs-q3 --grades .eval/grades-q3.json`：

| 方向 | 相关 | **必找** |
|---|---|---|
| 原句直搜 | 9 | 2 |
| 夫妻共同债务 共债共签 认定 | 8 | **0** |
| 夫妻一方借款 另一方 举证责任 | 5 | **0** |
| 民法典 1064条 夫妻共同债务 | 0 | 0 |
| **最高人民法院 夫妻债务纠纷 解释** | 9 | **7** |

**9 篇必找里有 7 篇来自同一个"文书名/发布机关"型方向**；而三个"主题词"型方向（正是规划器产出的那种）
**合计 0 篇必找**。所以不是排序问题、不是预算问题、也不是精选口味问题 ——
**是查询改写策略的系统性盲区**：把问题改写成主题词，就必然只捞到主题词的公众号普法文。

### 给"一手优先"prompt 划出边界

同一份 q3 数据上跑精选两臂：

| 候选集 | current 必找命中 | authority 必找命中 |
|---|---|---|
| 真实生产 12 篇（必找 **0**） | 0/3 | **0/3**（无从下手，prompt 是空转） |
| 并集 48 篇（必找 9） | 2/3（nDCG 86.6%） | **3/3（nDCG 100%）** |

authority 在 48 篇上挑出的是：`最高法院:夫妻债务纠纷的解释及答记者问(2018)` ·
`最高院法官:审理夫妻债务纠纷案件如何适用新司法解释?` · `人民法院案例库:…` —— 全是一手/权威。

**结论（三题一致）**：一手优先 prompt 只在**候选集里真有一手来源**时起作用；
它替代不了召回。两条修复是**互补**的，缺一不可：

1. ✅ 已修：轮转 + 标题去重 → 相关性（q3 实测 10/12）
2. ✅ 已修：一手优先 prompt → 候选里有权威时的取舍（q1 3/3 · q2 2/3=上限 · q3 3/3）
3. ⬜ **未做**：规划器必须产出**至少一个"文书名/发布机关"型方向**
   （如 `最高人民法院 <主题> 解释/通知/纪要`）—— q3 实测那一个方向贡献了 7/9 必找

## 按检索方向归因：**轮转修复的收益被测出来了**（2026-10-01）

`pnpm tsx scripts/eval-wechat-search.ts directions --runs .eval/runs-q2 --grades .eval/grades-q2.json`

每个 capture run = 一个检索方向。q2（竞业限制）的归因：

| 方向 | 返回 | 净新增 | 其中相关 | 其中必找 |
|---|---|---|---|---|
| 原句直搜 | 10 | 10 | 7 | **0** |
| 竞业限制 继续履行 违约金 | 10 | 10 | 9 | 4 |
| 竞业限制 补偿金 未支付 效力 | 10 | 10 | **10** | **4** |
| 竞业限制 司法解释 三十八条 | **0** | 0 | 0 | 0 |
| 劳动者 违反竞业限制 用人单位 救济 | 10 | 10 | 6 | 1 |

同 12 篇预算，两种取法：

| 取法 | 构成 | 内容 |
|---|---|---|
| **轮转（修复后 = 当前生产实现）** | 3 / 3 / 3 / 0 / 3 | **10 相关 · 5 必找** |
| **顺序取（修复前）** | 原句直搜 ×10 · 方向2 ×2 | **9 相关 · 2 必找** |

**必找命中 2 → 5（×2.5）**，而且机理清楚：原句直搜这个方向**一条必找都没有**，
却在旧的"顺序取"下独占 10/12 个名额；最好的那个方向（10 相关 / 4 必找）**一篇都没进预算**。
轮转之后每个方向各拿 3 个名额，必找文章才进得来。

> 这条也**回溯解释了 q1 的异常**：生产那轮 12 篇的相关率（41.7%）比 pool 均值（62.7%）还差 ——
> 不是规划器方向差，而是**顺序取让第一个方向把名额吃光了**（q1 那轮还叠加了 url 去重失效）。
> 我当初修轮转时只有"+1 篇唯一"这点证据，现在才有真正的数字。

另外：`司法解释 三十八条` 这个方向**返回 0 篇** —— 搜狗不吃"法条编号式"关键词。
生产里规划器很容易产出这种查询（白跑一次页面加载，还占一个方向）。

## 换第二个真实问题复现：**「一手优先」站住了**（2026-10-01）

`scripts/eval-runs-ab.ts`（通用：吃任意 capture pool + **先于实验写好**的 grade 文件）

第二个问题（劳动法，与第一题的破产法不同域）：
> 员工离职后违反竞业限制入职竞争对手，原公司能否要求继续履行并主张违约金？公司未支付竞业限制补偿金是否影响？

检索方向在抓取前就写死（避免事后挑方向）：`竞业限制 继续履行 违约金` / `补偿金 未支付 效力` /
`司法解释 三十八条` / `劳动者 违反竞业限制 用人单位 救济`（**其中 `司法解释 三十八条` 返回 0 篇**
—— 搜狗不吃这种"法条编号式"查询，这本身是个可记的通道特性）。

| 臂 | 候选数 | 视野内相关 | 视野内必找 | precision@3 | 必找命中 | nDCG |
|---|---|---|---|---|---|---|
| current@12 | 12 | 9 | 2 | 100% | **1/3** | 69.7% |
| current@全部 | 40 | 32 | 9 | 100% | 2/3 | 73.2% |
| **authority@12** | 12 | 9 | 2 | 100% | **2/3** | **86.6%** |
| authority@全部 | 40 | 32 | 9 | 100% | 2/3 | 86.6% |

**同一批 12 篇候选、只换 prompt：必找命中 1/3 → 2/3，nDCG 69.7% → 86.6%。**
注意 @12 的候选里**只有 2 篇 grade=3**，所以 2/3 就是**这一档的理论上限** —— authority 打满了。
作为对照，q1 是 2/3 → 3/3、73.2% → 100%。**方向一致，幅度不同。**

一个额外的反例（值得盯着）：@全部 时候选里 9 篇 grade=3 全都可见，两个 prompt **都只挑到 2/3**
—— 说明精选在"从很多好文章里挑最好的 3 篇"这件事上还有残差，不是加宽视野能解决的。

> ⚠ 同样的方法论警告：第二题的 grade 也是在跑任何精选臂**之前**写死的（见 `--grades` 的约束），
> 但标注仍是我打的 —— 两题效应方向一致能降低"碰巧"的概率，不能消除"同一个人设计 prompt 又打分"的偏差。
这条数字不需要任何人工标注就能算，因此每次改通道 / 改检索方向都能立刻对比。

## 指标怎么读

| 指标 | 含义 | 分母 |
|---|---|---|
| **pool 覆盖** | 本轮召回篇数 / pool 篇数 | **零标注可算**，用来量化"召回窄" |
| 判定覆盖 | `留 x/3 · 判 y/9` | 一眼看出 N/A 是"没标注"还是"表现差" |
| 通道召回 | asserted 标签中被召回的占比 | 只含标了 `asserted` 的 grade≥2 标签 |
| precision@k | kept 中已判定为相关的占比 | 只含**已判定**的 kept（没标注 → N/A，不误报 0%） |
| 必找保持 | 召回到的 grade=3 里被 kept 的占比 | 不含通道没搜到的（那算通道的账） |
| 误杀率 | dropped 中 grade≥2 的占比 | 只含**已判定**的 dropped |
| nDCG | 排序质量 | 理想序取自人工标注的 pool；`ranked=false` 时 N/A |
| 正文读到 | kept 中文正文字数达标的占比 | 只含记录了 readOk 的 kept |

## 顺带查出的生产问题

1. ✅ **已修（2026-10-01）：合并去重失效**。`wechat-search/route.ts` 原来按 url 去重，
   而 url 是搜狗的加密跳转链（同一篇每次 token 都不同）→ 重复副本白占 12 篇候选预算。
   修法落在 `src/lib/butler/wechat-dedupe.ts`（**生产与评测共用同一份口径**）+ GET 的合并段：
   按标题去重、**上限改为卡唯一条数**、每方向多取几条并**跨方向轮转**。
   真实数据上的前后对比（用 `.eval/runs` 里抓回来的候选回放）：

   | 场景 | 旧 perQuery | 旧唯一篇数 | 新 perQuery | 新唯一篇数 |
   |---|---|---|---|---|
   | 1 个方向（模型不可用 → 原句直搜，**降级路径**） | 6 | 6 | 10 | **10（+4）** |
   | 2 个方向 | 6 | 12 | 8 | 12 |
   | 3 个方向 | 4 | 11 | 6 | **12（+1）** |

   ⚠ **只改去重键的收益是 0**：旧上限数的是"原始条数"，3 方向 × 4 条正好凑满 12，
   所以必须在同一处把"上限卡唯一 + 多取原始 + 轮转"一起改。
   实测那一轮被副本占掉的名额，恰好是 `高院发布:…诉讼费缓交…通知` —— 就是被精选判掉的那条。
2. ✅ **已修（2026-10-01）：落库账本丢排序**。新增 `WechatSearchTraceItem.rank`（模型名次；
   兜底路径不写）。同时把账本组装从 enrich 路由抽到 `src/lib/butler/wechat-trace.ts` 并补了单测
   （它是 schema 的唯一边界，字段写错事后补不回来）。
   验证：同一份演示标注下，无 rank → `nDCG N/A`；有 rank（且名次**故意与召回序相反**）→
   `71.7%（6.393/8.917）` —— 若实现偷懒用召回序充数，这里会显示 100%。
3. **候选无发布时间**：桥只返回 `{title,url,account,snippet}`，而精选 prompt 要求按
   "时效较新"排序 —— 那是一条**无法执行的空指令**。
4. ✅ **已修（2026-10-01）：账本不记检索方向 → 召回无法归因**。
   规划器给的关键词串（`queries`）与意图（`intent`）原先只活在右栏内存里，
   于是"12 篇里只有 2 篇相关"**查不出是规划器方向不好、还是搜狗在该方向上的排序不好**。
   现在两者随账本落库（`WechatSearchTrace.queries` / `.intent`），链路是：
   GET 规划 → 抽屉 `wechatPlan` → enrich 请求体 → `recordSearchExchange` → 账本 → `roundFromTrace`
   → 评测报告 / `stats` 打印 / triage 的同域度计算。

   **怎么用它归因**（下一条新轮次落库后）：
   ```bash
   pnpm tsx scripts/eval-wechat-search.ts stats        # 直接打印本轮的方向
   pnpm tsx scripts/eval-wechat-search.ts score --runs .eval/runs
   ```
   - `queries` 只有一个元素且等于原句 → 规划器**没跑成**（模型不可用 → 原句直搜），
     这一轮的召回不能算在规划头上；
   - 有 3 个方向但某一方向贡献的候选一篇相关都没有 → 是**规划器**的问题（方向选错）；
   - 每个方向都贡献了相关候选、但预算被先到的方向占满 → 是**预算/轮转**的问题。
   老轮次没有这两个字段（`stats` 会明说"账本未记录"），所以只有新轮次能归因。

5. ⚠ **preset 里有不存在的模型 id（未改，待你决定）**：glm 的 `rerank-3` / `rerank-plus`
   在智谱侧都是 `400 1211 模型不存在`，唯一可用的是 `rerank`。这两个 id 会显示在设置界面里，
   谁照着它接一次就会踩空。改 preset 属产品可见变更，所以只记账不动手。

## 已知局限（别拿它当结论）

1. **`stats` 的同域度排序不是 oracle**。它是标题/摘要与原句的字符 bigram Jaccard。
   实测它**与 LLM 精选的偏差同向**：都偏向 snippet 里反复出现关键词的文章，
   而干巴巴的权威通知（snippet 只是标题的复述）两边都排后面。
   所以它只能当"人工复查队列"，不能当自动判定。
2. **pool 受通道上限约束**：搜狗单查询最多 10 篇，桥不接受翻页参数，
   所以 pool 无法无限扩大；`asserted` 里"谁都没搜到"的那些，只能靠人补。
   实测 5 个方向共 62 条 → 51 篇唯一，**方向之间的重复不多**（2/3/1/0/2），
   说明"多拆几个方向"确实能扩 pool，不是白费。
3. **一轮 12 篇的样本极小**。`n=1` 时任何比率都不该被引用；
   评测的价值在于**同一套 golden 上比较改动前后**，不是发布绝对精度。
4. **错误类型没区分**：目前不区分"判错"（相关被判掉）与"排序错"（相关但排在后面），
   `nDCG` 只覆盖后者，且只在 `ranked` 时可用。
5. **`asserted` 是人工判断，不是完备召回集**。你点名 10 篇，召回率的分母就是这 10 篇 ——
   它衡量"通道对你点名的篇目召回得如何"，不是"对全网相关文章召回得如何"。
   要更接近后者，只能持续多拆方向、扩 pool。

## capture 的副作用（重要）

`--via server` 会真实调用模型（计费），并且服务端会把这一轮**落库进常驻「小微」会话**
（见 `src/lib/core/butler-search.ts` 的 `recordSearchExchange`）——评测轮次会出现在聊天记录里。
批量跑之前先想清楚；只想建 pool 就用 `--via bridge`（不经模型、不落库）。
